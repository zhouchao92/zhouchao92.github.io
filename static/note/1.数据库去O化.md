# 数据库去O化

为了信创环境的建设，国内大部分软件系统都逐步要求数据库去O化，即 Oracle 数据库需要迁移至 MySQL、PostgreSQL、达梦数据库等开源或国产数据库。

> 目标库差异提示：达梦（DM）高度兼容 Oracle，改造量最小；OceanBase（MySQL 租户）、MySQL 与达梦语法体系接近；PostgreSQL 差异最大，需重点改写。下文 SQL 语法与类型映射均分别给出两套对照。

## 表结构迁移

借助 AI 对话，将导出的 Oracle 表结构转换为其他数据库的表结构，需要额外注意序列、主键、索引等信息，AI 转换后必须人工核对数据类型映射。

### 数据类型映射

#### Oracle → MySQL / 达梦（兼容 MySQL 体系）

| Oracle 类型                   | 目标库类型                                      | 说明                                                                |
|-------------------------------|-------------------------------------------------|---------------------------------------------------------------------|
| `NUMBER(p,0)`（p≤2/4/6/9/18） | `TINYINT`/`SMALLINT`/`MEDIUMINT`/`INT`/`BIGINT` | 按精度选整型，**不要全用 DECIMAL**（DECIMAL 为字符串存储，索引慢）  |
| `NUMBER(p,s)`                 | `DECIMAL(p,s)`                                  | 金额等定点数                                                        |
| `VARCHAR2(n)`                 | `VARCHAR(n)`                                    | 注意字节/字符语义，UTF-8 下中文占 3 字节，建议按实际最大长度 ×3     |
| `CHAR(n)`                     | `CHAR(n)` / `VARCHAR(n)`                        |                                                                     |
| `DATE`                        | `DATETIME`                                      | **Oracle DATE 含时分秒，等价于 DATETIME，切勿映射为 DATE 丢失时间** |
| `TIMESTAMP(n)`                | `DATETIME(n)`                                   | 微秒精度可能截断（如 6 位精度），需确认                             |
| `CLOB`                        | `TEXT` / `LONGTEXT`                             | 读写方式不同，Oracle 用 `DBMS_LOB`，目标库可当字符串                |
| `BLOB`                        | `BLOB` / `LONGBLOB`                             |                                                                     |
| `NUMBER` 裸类型               | `DECIMAL(38,10)`（保守估算）                    | 先评估实际精度，避免直接映射为 `DOUBLE` 产生浮点误差                |

#### Oracle → PostgreSQL

| Oracle 类型    | PostgreSQL 类型                | 说明                                                                          |
|----------------|--------------------------------|-------------------------------------------------------------------------------|
| `NUMBER(p,0)`  | `INTEGER` / `BIGINT`           | 同 MySQL，整数用整型                                                          |
| `NUMBER(p,s)`  | `NUMERIC(p,s)`                 |                                                                               |
| `VARCHAR2(n)`  | `VARCHAR(n)`                   | 同样注意字符语义与 UTF-8 宽度                                                 |
| `DATE`         | `TIMESTAMP` / `TIMESTAMPTZ`    | **关键陷阱**：PG 的 `DATE` 只存日期，必须映射为 `TIMESTAMP`，否则时间信息丢失 |
| `TIMESTAMP(n)` | `TIMESTAMP(n)` / `TIMESTAMPTZ` |                                                                               |
| `CLOB`         | `TEXT`                         |                                                                               |
| `BLOB`         | `BYTEA`                        |                                                                               |
| `INTERVAL`     | 无对应                         | 应用层计算时间差                                                              |

### 其他需要核对的要点

- **序列 / 自增**：Oracle 用 `SEQUENCE` + 触发器/`.NEXTVAL`，迁移后：
  - MySQL / 达梦：`AUTO_INCREMENT`（单表自增）；
  - PostgreSQL：`nextval('seq')` 或 `GENERATED ALWAYS AS IDENTITY`。
  - 多表共用一个序列（全局唯一 ID）时，目标库需在应用层实现 ID 生成器（如雪花算法）。
  - 全量导入后必须校正序列起点：`MySQL` 重置 `AUTO_INCREMENT`；`PostgreSQL` 执行 `setval()`，否则新插入会主键冲突。
- **字符集**：Oracle 源端若为 `WE8MSWIN1252` 等编码，转到 `UTF-8` 时中文可能乱码。目标库统一使用 `utf8mb4`，迁移前确认两端字符集与排序规则。
- **主键**：Oracle 表可无主键，MySQL / OceanBase 建议必须带有自增或主键列。
- **索引与行长度**：MySQL 单行最大 65535 字节（受字符集影响）；Oracle 索引实现与 MySQL 不同，索引需按规范重新定义并在测试环境校验（避免出现 `Row size too large` 错误）。

### 分区表

Oracle 分区能力丰富（范围、列表、哈希、复合/子分区、间隔分区 interval、自动列表分区、引用分区等）。迁移时需注意目标库差异：

- **MySQL**：支持 RANGE / LIST / HASH / 子分区（KEY），但**不支持 interval（间隔）分区、自动列表分区、虚拟列分区**。间隔分区可用事件或存储过程模拟。
- **PostgreSQL**：10+ 提供声明式分区（RANGE / LIST / HASH），同样不支持引用分区表的外键、间隔分区等；部分版本对分区键类型（如 TIMESTAMP）有限制。
- **迁移工具限制**：AWS SCT 等工具通常**不自动转换分区 DDL**，需人工重写分区定义，并重新评估分区键、本地索引与全局索引的差异。

### 用户、权限与大小写敏感

| 维度         | Oracle                      | MySQL                                         | PostgreSQL                                 |
|--------------|-----------------------------|-----------------------------------------------|--------------------------------------------|
| 用户与模式   | 用户即模式（user = schema） | 用户为 `user@host`，与库分离                  | 用户与 schema 分离，需单独 `CREATE SCHEMA` |
| 对象名大小写 | 默认转大写、不区分          | 取决于 `lower_case_table_names`（默认不区分） | 未加双引号统一转小写、区分大小写           |
| 权限模型     | 角色/权限体系独立           | 库级/表级授权，含 host 维度                   | 角色/模式级授权                            |

迁移注意：应用中若依赖大小写敏感的对象名或 `SELECT "Col"` 双引号写法，迁到 PostgreSQL 时需统一为小写或显式加双引号；Oracle 的 `user.table` 写法在 MySQL/PG 需改为 `schema.table`。

## SQL 语法

### 语法对照（Oracle / MySQL·达梦 / PostgreSQL）

业务 SQL 中常见的 Oracle 独有函数或语法，需人工逐条核对改写。

| 语法 / 函数   | Oracle                               | MySQL / 达梦                          | PostgreSQL                                  |
|---------------|--------------------------------------|---------------------------------------|---------------------------------------------|
| 哑表 DUAL     | `SELECT 1 FROM DUAL`                 | 可省略，直接 `SELECT 1`               | 省略，直接 `SELECT 1`                       |
| 判空          | `NVL(a, b)`                          | `IFNULL(a, b)`（多值用 `COALESCE`）   | `COALESCE(a, b)`                            |
| 条件分支      | `DECODE(c, v1, r1, def)`             | `CASE WHEN c=v1 THEN r1 ELSE def END` | 同 MySQL                                    |
| 当前时间      | `SYSDATE`                            | `NOW()`                               | `NOW()` / `CURRENT_TIMESTAMP`               |
| 行限制 / 分页 | `WHERE ROWNUM <= 10`                 | `LIMIT 10`（排序分页见下）            | `LIMIT 10`                                  |
| 层次查询      | `CONNECT BY PRIOR ...`               | `WITH RECURSIVE ...`                  | `WITH RECURSIVE ...`                        |
| 日期→字符     | `TO_CHAR(d,'YYYY-MM-DD HH24:MI:SS')` | `DATE_FORMAT(d,'%Y-%m-%d %H:%i:%s')`  | `TO_CHAR(d,'YYYY-MM-DD HH24:MI:SS')`        |
| 字符→日期     | `TO_DATE(s,'YYYY-MM-DD')`            | `STR_TO_DATE(s,'%Y-%m-%d')`           | `TO_DATE(s,'YYYY-MM-DD')`                   |
| 月份加减      | `ADD_MONTHS(d, 3)`                   | `DATE_ADD(d, INTERVAL 3 MONTH)`       | `d + INTERVAL '3 months'`                   |
| 截断日期      | `TRUNC(d)`                           | `DATE(d)`                             | `DATE_TRUNC('day', d)`                      |
| 序列取值      | `seq.NEXTVAL`                        | `AUTO_INCREMENT` / 触发器调用         | `nextval('seq')` 或 `GENERATED AS IDENTITY` |
| 外连接        | `a.id = b.id (+)`                    | 标准 `LEFT JOIN`                      | 标准 `LEFT JOIN`                            |

> 达梦（DM）在语法上与 MySQL 体系基本一致，故与 MySQL 合并为一列；PostgreSQL 差异较大单独成列。字符串聚合（LISTAGG）与 MERGE/UPSERT 写法较多，单独见下方小节。

分页示例（按 id 排序取前 10）：

```sql
-- Oracle
SELECT * FROM (SELECT * FROM t ORDER BY id) WHERE ROWNUM <= 10;
-- MySQL / 达梦 / PostgreSQL
SELECT * FROM t ORDER BY id LIMIT 10;
```


### 公共陷阱（重点）

1. **空字符串与 NULL 不等价**：Oracle 中 `'' = NULL` 成立（空串即 NULL），而 MySQL、PostgreSQL 中 `'' <> NULL`。凡涉及空串判断的逻辑（`IS NULL`、汇总查询、唯一约束）都可能结果不一致，需改写为 `IS NULL OR col = ''`。
2. **隐式类型转换**：Oracle 宽松（NUMBER 与 VARCHAR 可自动互转），MySQL/PostgreSQL 严格，迁移时要显式 `CAST`，否则运行时报 `operator does not exist` 等错误。
3. **子查询必须取别名**：MySQL/PostgreSQL 要求派生表有别名。
4. **字段别名**：`AS` 后为空或含特殊字符时需加引号/反引号处理。
5. **字符集与排序规则**：迁移前后不一致会导致中文乱码或关联查询性能/结果异常。

### MERGE / UPSERT

Oracle 常用 `MERGE` 做「存在则更新、不存在则插入」，目标库需改写：

```sql
-- Oracle
MERGE INTO t USING (SELECT 1 AS id FROM dual) s ON (t.id = s.id)
WHEN MATCHED THEN UPDATE SET t.name = 'x'
WHEN NOT MATCHED THEN INSERT (id, name) VALUES (1, 'x');

-- MySQL：INSERT ... ON DUPLICATE KEY UPDATE（冲突列需有 PK / 唯一约束）
INSERT INTO t(id, name) VALUES (1, 'x')
  ON DUPLICATE KEY UPDATE name = 'x';
-- MySQL 8.0.19+ 推荐用别名：... AS new ON DUPLICATE KEY UPDATE name = new.name

-- PostgreSQL：INSERT ... ON CONFLICT（PG 15+ 也支持原生 MERGE）
INSERT INTO t(id, name) VALUES (1, 'x')
  ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name;
```

注意事项：
- 目标表**冲突列必须有主键或唯一约束**，否则 MySQL 报重复键、PG 报 `there is no unique or exclusion constraint`。
- Oracle `MERGE` 可同时含 `DELETE` 子句，PG `ON CONFLICT` 不支持 DELETE，需用 CTE 拆分；PG 15+ 的 `MERGE` 才支持。
- **避免使用 `REPLACE INTO`**：它会先删后插，重置自增主键、触发 DELETE 触发器、破坏外键，应改用 `ON DUPLICATE KEY UPDATE`。

### 字符串聚合（LISTAGG）

| Oracle                                          | MySQL                                          | PostgreSQL                          |
|-------------------------------------------------|------------------------------------------------|-------------------------------------|
| `LISTAGG(col, ',') WITHIN GROUP (ORDER BY col)` | `GROUP_CONCAT(col ORDER BY col SEPARATOR ',')` | `STRING_AGG(col, ',' ORDER BY col)` |

- PostgreSQL 的 `STRING_AGG` 返回 TEXT，容量较充裕；`wm_concat` 同样对应 `GROUP_CONCAT`（MySQL）/ `STRING_AGG`（PG）。
- EDB Postgres Advanced Server（兼容 Oracle 的 PG 发行版）可直接支持 `LISTAGG`，迁移成本更低。
- 超长拼接在 Oracle 会报 `ORA-01489`，目标库可通过截断或应用层聚合规避。

### 窗口函数与优化器 Hint

- **窗口函数**：`ROW_NUMBER()`、`RANK()`、`LAG()`、`LEAD()` 等在 MySQL 8.0+ 与 PostgreSQL 中均支持，多数可直接迁移；但需确认目标库版本（MySQL 5.7 及更早不支持窗口函数）。
- **优化器 Hint 不可移植**：Oracle 的 `/*+ INDEX(...) */`、`/*+ PARALLEL(...) */` 等 Hint 语法在 MySQL / PostgreSQL 中完全不同或不被原生支持，**切勿直接搬运**。应改为在目标库重新分析执行计划，必要时使用目标库对应写法（如 MySQL `/*+ ... */`、PG 借助 pg_hint_plan 扩展）。

## 数据全量同步

### Kettle

一般借助 Kettle 的「表输入」和「表输出」组件实现全量迁移。性能参数可通过 shell 脚本指定 JVM 参数（如 `-Xms`、`-Xmx`、`-XX:MaxPermSize`）提升迁移效率。

### DataX

Alibaba 开源工具 [DataX](https://github.com/alibaba/DataX)，采用 JSON 配置源/目标库类型、性能参数与业务 SQL，可快速完成数据迁移与业务切换。详见下文「开源工具」。

### 其他方案

- **阿里 DTS / OceanBase OMS**：支持结构迁移、全量迁移、增量同步（CDC）一体化，适合不停机平滑迁移。
- **oracle_to_mysql**：开源工具，支持在线迁移表、视图、索引、触发器、外键、自增列；不支持存储过程、函数、分区表、物化视图等，需手动处理。
- **Navicat / PowerDesigner**：可用模型设计工具将 Oracle 模型转换为目标库模型再生成 DDL。
- **增量同步**：完成全量后，通过 LogMiner / CDC 捕获源端变更（INSERT/UPDATE/DELETE）追平数据，再切换业务。

## 存储过程迁移

一般存储过程由 Oracle 定时任务触发，改造时通过 Java 程序实现。结合执行耗时与内存占比，采用两种调度方式：

- 耗时严重或内存占用高的任务，采用 **Spring Boot 定时调度**（部署在虚拟主机），可用条件注解 + 动态 cron 表达式配置。
- 耗时不高或内存占用低的任务，采用 **XXL-JOB** 方式，最大限度部署上云。

### PL/SQL 改写为目标库存储过程（可选路径）

若选择在目标库保留存储过程，需按目标库语法改写：

| Oracle 特性               | MySQL / 达梦                                   | PostgreSQL                            |
|---------------------------|------------------------------------------------|---------------------------------------|
| `PACKAGE`                 | 拆分为独立存储过程/函数，去掉包体与包级变量    | 用 SCHEMA 组织，或拆分为独立函数/过程 |
| `EXCEPTION WHEN`          | `DECLARE ... HANDLER`                          | `EXCEPTION WHEN ... THEN`（PL/pgSQL） |
| `RAISE_APPLICATION_ERROR` | `SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT=...` | `RAISE EXCEPTION`                     |
| `SYS_REFCURSOR`           | 游标或直接查询返回结果集                       | 游标 / `RETURN QUERY`                 |
| `CONNECT BY`              | `WITH RECURSIVE`                               | `WITH RECURSIVE`                      |
| `DUAL`                    | 去除                                           | 去除                                  |

注意：触发器、DBLINK、同义词、物化视图等特性目标库支持度不同（如分析型库不支持事务/触发器），需逐一评估替代方案，必要时上提到应用层实现。

## 数据校验

改完代码只是第一步，真正的考验是数据验证，建议做**三层校验**：

1. **行数对比**：源端与目标端每张表行数必须一致（脚本批量比对）。
2. **抽样逐字段比对**：随机抽取每张表约 100 行，重点核对 `NUMBER→DECIMAL` 精度、`DATE→DATETIME/TIMESTAMP` 的时分秒、字符集。
3. **业务校验**：用核心业务 SQL 在两端分别执行并比对结果。

常见校验失败根因：空字符串陷阱、字符集不一致、隐式类型转换、序列起点未校正。

## 事务与并发差异

迁移后运行期行为差异往往比语法更难发现，需重点关注：

### 默认隔离级别

| 数据库         | 默认隔离级别                          | 说明                                       |
|----------------|---------------------------------------|--------------------------------------------|
| Oracle         | READ COMMITTED（一致性读 / snapshot） | 每条语句看到查询开始前的已提交数据         |
| MySQL (InnoDB) | REPEATABLE READ                       | 事务内首次读建立快照，防止不可重复读与幻读 |
| PostgreSQL     | READ COMMITTED                        | 每条语句独立快照                           |

同一段应用代码迁移到不同目标库，**默认隔离级别不同**可能导致结果不一致（例如 MySQL RR 下两次读结果一致，PG RC 下可能不同）。需在连接配置或会话中显式设定预期级别。

### 「串行化」并非等价

- Oracle 的 `SERIALIZABLE` 实为**快照隔离（Snapshot Isolation）**，并非真正可串行化；它无法阻止「写偏斜（write skew）」。
- PostgreSQL 的 `SERIALIZABLE` 是真正的 **SSI（Serializable Snapshot Isolation）**，会通过谓词锁检测冲突并回滚（应用需重试，`SQLSTATE 40001`）。
- 若业务依赖「先读后写」的不变量（如余额校验、库存扣减），在 Oracle 上靠快照隔离「恰好正确」的逻辑，迁到目标库后可能暴露写偏斜问题，应显式提升隔离级别或加 `SELECT ... FOR UPDATE` 悲观锁。

### 锁与并发

- MySQL 在 RR 下使用 **gap / next-key lock**，会对索引间隙加锁，可能导致 INSERT 出现意外锁等待甚至死锁。
- PostgreSQL 依赖 MVCC，读写互不阻塞，冲突时通常靠事务重试而非锁等待。
- Oracle 在 RC 冲突时会**重跑整条查询**以保证一致，PostgreSQL 只重算被锁定的行，二者异常表现不同。

### 迁移建议

- 明确目标库的默认隔离级别，对关键事务显式声明。
- 对一致性要求高的路径，使用 `SERIALIZABLE` 或悲观锁，并为 PG 实现事务重试机制。
- 压测阶段重点观察死锁与锁等待日志（MySQL `innodb_lock_wait_timeout`、PG 日志中的 `could not serialize access`）。

## 开源工具

### DataX

Alibaba 的开源工具 [DataX](https://github.com/alibaba/DataX)，采用 JSON 配置数据库类型、性能参数与业务 SQL，可在短时间内完成数据迁移与业务切换。

DataX 结合 Python 定时调度框架（APScheduler）实现定时调度。启动命令 `python python_filepath cron_filepath`，其中 `cron_filepath` 使用 **6 位 cron 表达式（分 时 日 月 周）+ 脚本路径** 配置任务，例如：

```text
*/1 * * * * echo "[$(date +'%Y-%m-%d %H:%M:%S')] datax heartbeat"
```

上述配置即每分钟输出一次心跳，用于监测调度服务可用性。

> 依赖安装：`pip install apscheduler`
> 说明：脚本将每行配置解析为 APScheduler 的 `cron` 任务，其中第一位（秒）固定为 `0`，其余五位对应标准 5 位 cron；`max_instances` 按任务数 +1 设置以支持并发执行多个任务。

```python
# -*- coding: utf-8 -*-
import logging
import subprocess
import argparse
from apscheduler.schedulers.blocking import BlockingScheduler
from apscheduler.executors.pool import ThreadPoolExecutor

# 创建一个 logger
logger = logging.getLogger()
logger.setLevel(logging.INFO)

# 创建一个文件处理器，用于写入日志文件
file_handler = logging.FileHandler('/usr/local/datax/log/python.log')
file_handler.setLevel(logging.INFO)

# 创建一个流处理器，用于输出到控制台
stream_handler = logging.StreamHandler()
stream_handler.setLevel(logging.INFO)

# 定义日志格式
formatter = logging.Formatter('%(asctime)s %(levelname)s %(module)s: %(message)s')

# 设置处理器的格式
file_handler.setFormatter(formatter)
stream_handler.setFormatter(formatter)

# 将处理器添加到 logger
logger.addHandler(file_handler)
logger.addHandler(stream_handler)


"""解析文件的单行任务，返回 cron 表达式和命令"""
def parse_crontab_line(line):
  """parse single line configuration like crontab"""
  parts = line.split()

  if len(parts) < 6:
    logger.info("Invalid crontab line format, content:{}".format(parts))
    return None, None
  schedule = '0 ' + ' '.join(parts[:5])
  command = ' '.join(parts[5:])
  return schedule, command.strip()


"""python 执行 shell 命令"""
def execute_command(command):
  """execute shell command"""
  try:
    process = subprocess.Popen(command, shell=True, stdout=subprocess.PIPE, stderr=subprocess.PIPE)
    stdout, stderr = process.communicate()
    return_code = process.returncode

    if stderr:
      logger.error(stderr.decode('utf-8'))
    logger.info("Command {} return Code:{}".format(command, return_code))
  except Exception as e:
    logger.error("Error executing command:{}".format(e))


"""加载文件内容"""
def load_tasks(filename):
  """load tasks from the file"""
  tasks = []
  with open(filename) as file:
    for line in file:
      line = line.strip()
      if line and not line.startswith('#'):
        schedule, command = parse_crontab_line(line)
        if schedule and command:
          logger.info("Add task command: {}, schedule: {}".format(command, schedule))
          tasks.append((schedule, command))
  return tasks


"""主进程入口"""
def main():
  parser = argparse.ArgumentParser(description="Load enhanced crontab-like tasks (including seconds) from a file and execute them using APScheduler.")
  parser.add_argument('filename', type=str, help='The path to the configuration file containing crontab-like tasks')

  args = parser.parse_args()

  tasks = load_tasks(args.filename)

  max_instances = len(tasks) + 1
  executors = {
      'default': ThreadPoolExecutor(max_instances)
  }
  scheduler = BlockingScheduler(executors=executors)

  for task in tasks:
    schedule, command = task
    schedule_parts = schedule.split()
    scheduler.add_job(execute_command, 'cron', args=[command],
                      second=schedule_parts[0], minute=schedule_parts[1], hour=schedule_parts[2],
                      day=schedule_parts[3], month=schedule_parts[4], day_of_week=schedule_parts[5], max_instances=max_instances)

  try:
    scheduler.start()
  except (KeyboardInterrupt, SystemExit):
    logger.info('Scheduler exception...')


if __name__ == '__main__':
  main()
```

## 迁移实施建议

建议按以下顺序推进，顺序不要乱：

1. **兼容性评估**：扫描代码中 `ROWNUM`、`FROM DUAL`、`NVL`、`DECODE`、`(+)`、`CONNECT BY`、`SYSDATE`、`ADD_MONTHS`、`TO_DATE` 等 Oracle 方言出现频次，评估改造范围。
2. **制定类型映射规则**：明确 `NUMBER`/`VARCHAR2`/`DATE`/`CLOB` 等到目标库的映射，确定序列/自增方案。
3. **表结构迁移**：AI 辅助转换 + 人工核对（见「表结构迁移」）。
4. **存储过程改写**：PL/SQL → Java 定时任务，或改写为目标库过程（见「存储过程迁移」）。
5. **数据迁移**：Kettle / DataX / DTS 完成全量，必要时增量追平。
6. **三层数据校验**：行数、抽样、业务校验，确保数据一致。
7. **业务切换**：低峰期切换，保留回滚方案。

> 信创选型小结：达梦兼容 Oracle 改造量最小；OceanBase / MySQL 体系需重点处理类型与语法；PostgreSQL 差异最大，建议优先在应用层消解 Oracle 专有特性。
