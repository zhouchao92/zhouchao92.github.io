# 微服务端到端自监控

分布式下，微服务监控可以按照 POD 运行状况（CPU 占用率、内存占用率）、中间件性能、第三方系统（接口、文件服务器）通断性、业务状况等方面进行监控。完整的端到端自监控应覆盖可观测性三支柱——**Metrics（指标）、Tracing（链路）、Logging（日志）**，并通过统一元数据（如 `TraceId`、服务名、实例 IP）将三者关联，形成从基础设施到业务层的端到端视图（[通义千问-端到端自监控](https://tongyi.aliyun.com/qianwen/share?shareId=7f78f6c0-59e1-4795-ad82-ad14957d6fee)）。


## 监控哪些性能指标？

### POD 性能

对于单个 POD 的 CPU 占用率和内存占用率，可以通过采用 Prometheus 来采集与获取数据，也可以基于 Java 原生语法调用相应的 shell 命令来获取。容器微服务自身的健康状态，可以依赖 Spring Boot Actuator 相关接口实现。


#### Prometheus 获取 POD 内存占用率

```promql
(
  sum(avg_over_time(container_memory_working_set_bytes{namespace="{namespace}", pod=~"{podName}", container=""}[5m])) by (pod)
)
/
(
  sum(kube_pod_container_resource_limits_memory_bytes{namespace="{namespace}", pod=~"{podName}"}) by (pod)
) * 100

```

#### Prometheus 获取 CPU 内存占用率

```promql
(
  sum(rate(container_cpu_usage_seconds_total{namespace="{namespace}", pod=~"{podName}", container=""}[5m])) by (pod)
)
/
(
  sum(container_spec_cpu_quota{namespace="{namespace}", pod=~"{podName}", container=""} 
      / 
      container_spec_cpu_period{namespace="{namespace}", pod=~"{podName}", container=""}) by (pod)
) * 100
```


### 中间件

- Redis：连接数、内存占用与淘汰、缓存命中率、命令执行时间、错误率
- ElasticSearch：延迟、吞吐量、磁盘空间使用情况、集群与节点健康状态
- 消息队列：生产和消费速度、堆积情况、消息延迟
- 数据库：SQL查询性能（慢 SQL）、数据库连接池使用情况与活跃会话数、数据库表的增长、磁盘I/O性能
- FTP/SFTP服务器：网络连通性、服务器资源情况


### 第三方系统

- 接口连通性：定时通过 ping、telnet 等脚步命令或 Java 的 Scoket 套接字（IP + PORT）测试系统间的网络连通情况，另外也可约定非业务接口来测试验证网络


### 业务状况

- 内部微服务 feign 接口调用与第三方系统业务接口调用，将请求信息包括请求地址、请求入参、请求头、响应信息等核心数据持久化，可采取以下几种策略
	- log4j2 写入日志文件，定时压缩存储 ftp/sftp
	- 异步写入 ES 和数据库表记录 
	- log4j2/filebeat 先写入 kafka，再消费写入 ES 和 数据库接口记录表


## 端到端全链路追踪（Tracing）

仅监控 Metrics 只能知道「某个服务有问题」，无法定位根因。端到端全链路追踪通过贯穿一次请求在多个服务、组件间的调用路径，把指标、日志、链路关联起来（[阿里云-性能监控与全链路追踪最佳实践](https://help.aliyun.com/zh/document_detail/2536111.html)）。

- **三支柱（Three Pillars）**：Metrics（指标，Prometheus）、Tracing（链路，调用链）、Logging（日志），三者通过 `TraceId`/`SpanId`、资源标签关联，形成「拓扑大图」。
- **统一标准**：OpenTelemetry（OTel）已成为云原生可观测性的事实标准，提供供应商中立的 SDK、Collector 与协议；链路上下文透传推荐采用 **W3C TraceContext（Traceparent 头）**，并兼容 B3、Jaeger、SkyWalking（sw8）等协议。
- **前后端打通**：前端 RUM（真实用户监控）SDK 注入链路头，后端 APM 反查前端「第一跳」，实现浏览器/小程序 → 网关 → 微服务 → 中间件 的完整链路闭环（[腾讯云-RUM+APM 全链路](https://cloud.tencent.com/developer/article/2495412)）。
- **无侵入接入**：Java 应用优先使用 SkyWalking / ARMS Agent 字节码增强，无需改造代码即可自动埋点；非 Java 应用通过 OTel SDK 主动埋点。
- **链路筛选与诊断**：按 `TraceId`、应用名、接口名、耗时、状态码、自定义标签过滤 → 查看调用轨迹 + 本地方法栈 + 关联 SQL/业务日志 → 必要时结合内存快照、Arthas 在线诊断二次分析。
- **典型透传头**

| 协议字段     | 说明                                 |
|--------------|--------------------------------------|
| Traceparent  | OpenTelemetry / W3C 约定字段（推荐） |
| sw8          | SkyWalking 约定字段                  |
| b3           | Zipkin 跟踪约定字段                  |
| Sentry-Trace | Sentry 约定字段                      |

- **业务链路**：除系统调用链外，还应把「下单、支付、履约」等业务动作建模为业务链路（业务 Trace），关联订单号、用户 ID 等业务标识，实现订单级追溯与用户级灰度、全链路压测隔离（[阿里云-业务链路最佳实践](https://www.alibabacloud.com/help/zh/arms/application-monitoring/user-guide/best-practices-for-a-business-trace)）。



## 如何配置性能指标？

### 应用层（Micrometer + Actuator + Prometheus）

Spring Boot 通过 `Actuator` 暴露端点，`Micrometer` 作为指标门面将指标输出为 Prometheus 格式，由 Prometheus 定时拉取（pull）。

1. 引入依赖 `micrometer-registry-prometheus` 与 `spring-boot-starter-actuator`。
2. 开放端点 `/actuator/prometheus`，Prometheus 通过 `scrape_configs` 抓取。
3. 自定义指标：`Counter`（请求计数）、`Timer`（耗时分布）、`Gauge`（瞬时值，如线程数/队列长度）、`DistributionSummary`（分布摘要）。

```java
@Timed(value = "biz.order.create", description = "创建订单耗时", histogram = true)
public Order create(OrderReq req) { ... }

Counter.builder("biz.thirdparty.call")
      .tag("api", "sms").register(registry).increment();
```


### 中间件 Exporter

各中间件通过官方/社区 Exporter 暴露指标，由 Prometheus 抓取：

- Redis：`redis_exporter`（连接数、内存、命中率、命令耗时）
- Elasticsearch：`elasticsearch_exporter`（集群健康、分片、JVM、索引延迟）
- Kafka/RocketMQ：`kafka_exporter` / `rocketmq_exporter`（堆积、生产消费速率、延迟）
- MySQL：`mysqld_exporter`（连接数、慢查询、QPS、Innodb 状态）
- 主机/容器：Node Exporter、`kube-state-metrics` + `cadvisor`


### 探针无侵入采集

使用 SkyWalking Agent、ARMS/Java Agent 或 eBPF 版监控，无需改代码即可采集 JVM、调用链、TCP 重传、On/Off-CPU 剖析等数据，适合存量系统快速补齐可观测能力。


### 第三方系统与连通性

- **云拨测（CAT）/Synthetic Monitoring**：利用分布全球的探测点，模拟真实用户访问接口、域名、端口，监测连通性、DNS、SSL 证书、首包时间，弥补内部定时 ping/telnet 视角盲区。
- **接口探活**：在网关或 Sidecar 处配置健康探针（liveness/readiness），结合约定非业务接口做网络通断验证。



## 异常怎么告警与通知？

### 告警引擎

Prometheus `Alertmanager`（或云厂商告警中心）统一负责告警的路由、分组、抑制与静默：

- **路由（Route）**：按标签（服务、环境、严重级别）分发到不同接收组。
- **分组（Group）** + **抑制（Inhibit）** + **静默（Silence）**：合并同类告警、抑制衍生告警、维护期静默，降低告警风暴与误报。
- **降噪与闭环**：通过 ChatOps（钉钉/飞书/企业微信群机器人）回写处理状态，形成告警处理闭环。


### 告警规则设计

- **阈值告警**：CPU/内存占用率、慢 SQL 数、消息堆积量、连接池使用率等超过阈值触发。
- **区间检测 / 智能异常检测**：基于历史基线做同比/环比，自动推荐阈值、识别突变（如错误率突增、P99 延迟劣化）。
- **业务指标告警**：业务链路失败率、关键接口错误码、订单创建耗时、第三方调用成功率等。
- **链路级告警**：错慢调用根因定位、依赖瓶颈分析（结合 Trace 模型异常检测）。


### 通知渠道

钉钉、飞书、企业微信、邮件、Webhook、Slack、PagerDuty（On-Call 值班）等；重要告警配合电话/短信升级策略。


### 告警分级示例

| 级别 | 场景                               | 通知方式           |
|------|------------------------------------|--------------------|
| P0   | 核心服务不可用、POD 频繁 OOMKilled | 电话 + 群 @ + 工单 |
| P1   | 错误率突增、消息堆积超阈值         | 群机器人 + 邮件    |
| P2   | 单实例 CPU/内存偏高、慢 SQL        | 群机器人           |
| P3   | 第三方接口偶发超时                 | 日报汇总           |

> 最佳实践：告警要「可行动」，每条告警应对应明确的处理动作与责任人；结合统一数据图谱消除指标/链路/日志数据孤岛，提升端到端排障效率。
