# 慢SQL分析与调优

本文详细介绍 MySQL 慢 SQL 分析与调优的完整流程，包括慢查询日志定位、EXPLAIN 执行计划分析、关键字段解读以及调优最佳实践。


## 一、慢 SQL 调优流程

慢查询日志定位 → EXPLAIN 分析执行计划 → 检查 type/key/Extra/Rows → 优化 SQL/索引 → 验证效果


## 二、慢查询日志

### 2.1 开启慢查询日志

```sql
-- 查看是否开启
SHOW VARIABLES LIKE 'slow_query_log';

-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;

-- 设置慢查询阈值（单位：秒）
SET GLOBAL long_query_time = 1;

-- 查看慢查询日志位置
SHOW VARIABLES LIKE 'slow_query_log_file';
```

### 2.2 配置文件设置

```ini
[mysqld]
slow_query_log = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1
log_queries_not_using_indexes = ON
```

### 2.3 使用 mysqldumpslow 分析

```bash
# 按查询时间排序，取前10条
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 按查询次数排序
mysqldumpslow -s c -t 10 /var/log/mysql/slow.log

# 按锁等待时间排序
mysqldumpslow -s l -t 10 /var/log/mysql/slow.log
```


## 三、EXPLAIN 执行计划

### 3.1 基本用法

```sql
EXPLAIN SELECT * FROM users WHERE id = 1;
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
```

### 3.2 EXPLAIN 输出字段

| 字段          | 说明                   |
|---------------|------------------------|
| id            | 查询序号               |
| select_type   | 查询类型               |
| table         | 表名                   |
| partitions    | 匹配的分区             |
| type          | 访问类型（重点）       |
| possible_keys | 可能使用的索引         |
| key           | 实际使用的索引（重点） |
| key_len       | 索引长度               |
| ref           | 索引比较的列或常量     |
| rows          | 预估扫描行数（重点）   |
| filtered      | 过滤百分比             |
| Extra         | 额外信息（重点）       |


## 四、type 字段详解（访问类型）

type 字段表示 MySQL 在表中找到所需行的方式，是评估查询性能的关键指标。

### 4.1 访问类型性能排序

```plaintext
system > const > eq_ref > ref > range > index > ALL
```

**性能从好到差，一般来说需要达到 range 级别，最好达到 ref 级别。**

---

### 4.2 system

**概念：**
- 表只有一行记录，是 const 的特例
- 通常只出现在 MyISAM 存储引擎的系统表中

**示例：**
```sql
-- MySQL 8.0+ 中 system 已很少出现，通常只有 MyISAM 引擎的元数据表才可能出现
-- InnoDB 引擎下即使表只有一行也会显示 const
EXPLAIN SELECT * FROM some_single_row_table WHERE id = 1;
-- type: const（InnoDB）或 system（MyISAM 单行表）
```

**特点：**
- 表数据量极小（通常为 1 行）
- MySQL 优化器直接读取，无需扫描

---

### 4.3 const

**概念：**
- 通过索引一次找到，用于 primary key 或 unique 索引
- 将主键或唯一索引的所有部分与常量比较，最多匹配一行数据
- 读取速度快，因为只读取一次

**示例：**
```sql
-- 主键查询（const）
EXPLAIN SELECT * FROM users WHERE id = 1;

-- 唯一索引查询（const）
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';

-- 注意：IN 查询返回多行时是 range，不是 const
EXPLAIN SELECT * FROM users WHERE id IN (1, 2, 3);
-- type: range（返回多行）
```

**特点：**
- 查询条件必须是主键或唯一索引
- 等值比较（=）
- 返回结果最多只有 1 行

---

### 4.4 eq_ref

**概念：**
- 类似于 ref，但使用的是唯一索引
- 对于每个索引键，表中只有一条记录与之匹配
- 常见于主键或唯一索引扫描
- 多表连接时，驱动表返回一行，被驱动表通过唯一索引匹配

**示例：**
```sql
-- 多表连接，orders 表的 user_id 是外键索引
EXPLAIN SELECT * FROM users u JOIN orders o ON u.id = o.user_id;

-- 被驱动表 orders 通过 user_id 唯一索引匹配
-- type 列会显示 eq_ref
```

**特点：**
- 多表连接场景
- 被驱动表使用主键或唯一索引
- 每次连接只匹配一行

---

### 4.5 ref

**概念：**
- 使用非唯一索引扫描，返回匹配某个单独值的所有行
- 索引键不是唯一的，可能有多个匹配
- 本质上也是一种索引访问，返回所有匹配某个值的行

**示例：**
```sql
-- 创建普通索引
CREATE INDEX idx_name ON users(name);

-- 普通索引查询
EXPLAIN SELECT * FROM users WHERE name = '张三';

-- 范围查询（不是 ref）
EXPLAIN SELECT * FROM users WHERE name > '张三';
```

**特点：**
- 使用普通索引（非唯一）
- 等值比较
- 可能返回多行数据

---

### 4.6 range

**概念：**
- 只检索给定范围的行，使用索引来选择行
- key 列显示使用了哪个索引
- 通常出现在 between、<、>、in、like 等查询中

**示例：**
```sql
-- 范围查询
EXPLAIN SELECT * FROM users WHERE id BETWEEN 1 AND 100;
EXPLAIN SELECT * FROM users WHERE id > 50;
EXPLAIN SELECT * FROM users WHERE id IN (1, 2, 3, 4, 5);

-- LIKE 模糊查询（前缀匹配）
EXPLAIN SELECT * FROM users WHERE name LIKE '张%';

-- 日期范围查询
EXPLAIN SELECT * FROM orders WHERE create_time BETWEEN '2024-01-01' AND '2024-12-31';
```

**特点：**
- 索引范围扫描
- 比全表扫描好很多
- 是常见的优化目标

---

### 4.7 index

**概念：**
- 全表索引扫描，遍历整个索引树
- 与 ALL 的区别是：index 只遍历索引树，ALL 是全表扫描
- 索引文件通常比数据文件小，所以 index 比 ALL 快

**示例：**
```sql
-- 前提：name 列有索引

-- 覆盖索引查询（只查询索引列）
EXPLAIN SELECT id, name FROM users;
-- type: index

-- 查询主键（主键也是索引）
EXPLAIN SELECT id FROM users;
-- type: index

-- 全索引扫描（name 有索引但使用 LIKE '%张%' 无法使用索引定位）
EXPLAIN SELECT name FROM users WHERE name LIKE '%张%';
-- type: index（扫描整个索引）
```

**特点：**
- 扫描整个索引
- 不读取数据行（覆盖索引时）
- 性能比 ALL 好，但仍然需要优化

---

### 4.8 ALL

**概念：**
- 全表扫描，MySQL 从头到尾读取整张表
- 性能最差，通常需要优化

**示例：**
```sql
-- 没有使用索引的查询
EXPLAIN SELECT * FROM users WHERE name LIKE '%张%';
EXPLAIN SELECT * FROM users WHERE id % 2 = 0;
EXPLAIN SELECT * FROM users;
```

**优化建议：**
- 添加合适的索引
- 避免使用 % 开头的模糊查询
- 避免对索引列使用函数或计算

---

### 4.9 type 字段总结

| type   | 说明                  | 性能 | 优化建议     |
|--------|-----------------------|------|--------------|
| system | 表只有一行            | 最优 | 无需优化     |
| const  | 主键/唯一索引等值查询 | 很好 | 无需优化     |
| eq_ref | 多表连接唯一索引匹配  | 很好 | 无需优化     |
| ref    | 普通索引等值查询      | 良好 | 一般可接受   |
| range  | 索引范围扫描          | 一般 | 可优化为 ref |
| index  | 全索引扫描            | 较差 | 需要优化     |
| ALL    | 全表扫描              | 最差 | 必须优化     |


## 五、key 字段详解

### 5.1 key 字段说明

- **possible_keys**：可能使用的索引（MySQL 估算的）
- **key**：实际使用的索引（优化器选择的）
- **key_len**：索引使用的字节数

### 5.2 key_len 计算规则

key_len 表示索引使用的字节数，计算规则如下：

```sql
-- 数据类型字节数：
-- INT：4 字节
-- BIGINT：8 字节
-- CHAR(n)：n * 字符集字节数（UTF8MB4 为 n * 4）
-- VARCHAR(n)：n * 字符集字节数 + 2（长度前缀）
-- TIMESTAMP：4 字节
-- DATETIME：8 字节

-- NULL 标志位：如果列允许 NULL，额外 +1 字节

-- 示例计算：
-- INT NOT NULL：4 字节
-- INT NULL：4 + 1 = 5 字节
-- VARCHAR(100) NOT NULL UTF8MB4：100 * 4 + 2 = 402 字节
-- VARCHAR(100) NULL UTF8MB4：100 * 4 + 2 + 1 = 403 字节
```

### 5.3 示例

```sql
-- 表结构
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100),
    INDEX idx_name (name),
    INDEX idx_email (email)
);

-- 查询
EXPLAIN SELECT * FROM users WHERE name = '张三';
-- key: idx_name
-- key_len: 402 (VARCHAR(100) UTF8MB4 + 2)
```


## 六、Extra 字段详解

### 6.1 常见 Extra 值

| Extra                 | 说明                   | 性能 |
|-----------------------|------------------------|------|
| Using index           | 覆盖索引，不需要回表   | 优秀 |
| Using where           | 使用 WHERE 过滤        | 良好 |
| Using temporary       | 使用临时表存储中间结果 | 较差 |
| Using filesort        | 使用文件排序           | 较差 |
| Using index condition | 索引条件下推（ICP）    | 良好 |
| Using join buffer     | 使用连接缓冲区         | 一般 |

### 6.2 Using index（覆盖索引）

```sql
-- 创建联合索引
CREATE INDEX idx_name_email ON users(name, email);

-- 覆盖索引查询（不需要回表）
EXPLAIN SELECT name, email FROM users WHERE name = '张三';
-- Extra: Using index

-- 非覆盖索引查询（需要回表）
EXPLAIN SELECT * FROM users WHERE name = '张三';
-- Extra: Using where
```

### 6.3 Using temporary（临时表）

```sql
-- 分组查询如果没有索引，会使用临时表
EXPLAIN SELECT name, COUNT(*) FROM users GROUP BY name;
-- 如果 name 没有索引，Extra 会显示 Using temporary

-- 优化：添加索引
CREATE INDEX idx_name ON users(name);
EXPLAIN SELECT name, COUNT(*) FROM users GROUP BY name;
-- Extra: Using index
```

### 6.4 Using filesort（文件排序）

```sql
-- 排序查询如果没有索引，会使用文件排序
EXPLAIN SELECT * FROM users ORDER BY name;
-- 如果 name 没有索引，Extra 会显示 Using filesort

-- 优化：添加索引
CREATE INDEX idx_name ON users(name);
EXPLAIN SELECT * FROM users ORDER BY name;
-- Extra: Using index
```

### 6.5 Using index condition（索引条件下推）

ICP（Index Condition Pushdown）将 WHERE 条件下推到存储引擎层，在索引层面过滤数据，减少回表次数。

**适用场景：联合索引中间列有范围查询，后面列需要过滤时**

```sql
-- 创建联合索引：name（等值）→ age（范围）→ email（过滤）
CREATE INDEX idx_name_age_email ON users(name, age, email);

-- ICP 示例：age 范围查询后，email 在存储引擎层过滤
EXPLAIN SELECT * FROM users 
WHERE name = '张三' AND age > 25 AND email = 'test@example.com';
-- Extra: Using index condition

/*
执行过程：
1. name = '张三'：通过索引精确定位
2. age > 25：范围查询，定位到一批数据
3. email = 'test@example.com'：在存储引擎层直接过滤（ICP），避免回表
*/
```

**对比：无 ICP 的情况**
- 如果没有 ICP，执行过程如下：
  - 1. name = '张三' AND age > 25：通过索引定位数据
  - 2. 回表读取完整行数据
  - 3. 在 Server 层过滤 email = 'test@example.com'

- 有 ICP 时：
  - 1. name = '张三' AND age > 25：通过索引定位数据
  - 2. 直接在索引中过滤 email = 'test@example.com'（不回表）
  - 3. 只对过滤后的数据回表


**ICP 不会触发的场景：**

```sql
-- 1. 查询条件都在索引前缀列（无范围查询）
CREATE INDEX idx_name_email ON users(name, email);
EXPLAIN SELECT * FROM users WHERE name = '张三' AND email = 'test@example.com';
-- Extra: Using index（覆盖索引）或 Using where

-- 2. 第一个条件就是范围查询
CREATE INDEX idx_name_age ON users(name, age);
EXPLAIN SELECT * FROM users WHERE name > '张三' AND age = 25;
-- Extra: Using where（无法使用索引定位）
```


## 七、Rows 字段详解

### 7.1 Rows 字段说明

- **rows**：MySQL 估算需要检查的行数
- 是一个估算值，不是精确值
- 数值越小越好

### 7.2 如何使用 Rows 字段

```sql
-- 查看执行计划
EXPLAIN SELECT * FROM orders WHERE user_id = 100;

-- rows: 100 表示 MySQL 估算需要扫描 100 行
-- 如果实际扫描行数远大于这个值，可能需要优化

-- 使用 SHOW WARNINGS 查看实际执行的 SQL
SHOW WARNINGS;
```

### 7.3 Rows 优化策略

- 添加合适的索引减少扫描行数
- 使用覆盖索引避免回表
- 避免全表扫描（ALL）


## 八、调优最佳实践

### 8.1 索引优化

```sql
-- 1. 创建合适的索引
CREATE INDEX idx_user_id ON orders(user_id);

-- 2. 使用联合索引
CREATE INDEX idx_user_status ON orders(user_id, status);

-- 3. 避免索引失效
-- 不要对索引列使用函数
SELECT * FROM users WHERE YEAR(create_time) = 2024;  -- 索引失效
SELECT * FROM users WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01';  -- 索引有效

-- 不要对索引列进行计算
SELECT * FROM users WHERE id + 1 = 10;  -- 索引失效
SELECT * FROM users WHERE id = 9;  -- 索引有效
```

### 8.2 SQL 优化

```sql
-- 1. 避免 SELECT *
SELECT id, name FROM users WHERE id = 1;  -- 好
SELECT * FROM users WHERE id = 1;  -- 差

-- 2. 避免 OR 改用 UNION
-- 差
SELECT * FROM users WHERE id = 1 OR name = '张三';
-- 好
SELECT * FROM users WHERE id = 1
UNION
SELECT * FROM users WHERE name = '张三';

-- 3. 避免使用 !=
SELECT * FROM users WHERE id != 1;  -- 可能索引失效
SELECT * FROM users WHERE id IN (2, 3, 4);  -- 更好

-- 4. 避免使用 OR 导致索引失效
SELECT * FROM users WHERE id = 1 OR name = '张三';  -- 索引失效
SELECT * FROM users WHERE id = 1
UNION ALL
SELECT * FROM users WHERE name = '张三';  -- 索引有效
```

### 8.3 EXISTS 改写 IN

当子查询结果集较大时，EXISTS 通常比 IN 性能更好：

```sql
-- 示例表结构
-- users 表：id, name, dept_id
-- departments 表：id, name

-- 场景1：查询在"技术部"工作的所有员工

-- 方式1：IN（子查询结果集小时效率高）
SELECT * FROM users 
WHERE dept_id IN (
    SELECT id FROM departments WHERE name = '技术部'
);

-- 方式2：EXISTS（子查询结果集大时效率高）
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM departments d 
    WHERE d.id = u.dept_id AND d.name = '技术部'
);

-- 场景2：查询有订单的所有用户

-- 方式1：IN
SELECT * FROM users 
WHERE id IN (
    SELECT DISTINCT user_id FROM orders
);

-- 方式2：EXISTS（推荐，users 表大时效率高）
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- 场景3：查询没有订单的用户

-- 方式1：NOT IN（可能有 NULL 问题）
SELECT * FROM users 
WHERE id NOT IN (
    SELECT user_id FROM orders
);

-- 方式2：NOT EXISTS（推荐）
SELECT * FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- 方式3：LEFT JOIN（推荐）
SELECT u.* FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;
```

**EXISTS vs IN 选择原则：**

| 场景 | 推荐方式 | 原因 |
|------|----------|------|
| 子查询结果集小 | IN | 子查询只执行一次，结果集小效率高 |
| 子查询结果集大 | EXISTS | 外表小内表大，EXISTS 可短路 |
| 外表小内表大 | EXISTS | EXISTS 逐行检查，外表小扫描少 |
| 外表大内表小 | IN | IN 只执行一次子查询 |
| 涉及 NULL 值 | EXISTS | NOT IN 遇到 NULL 会返回空集 |

### 8.4 表结构优化

```sql
-- 1. 选择合适的数据类型
-- 使用 INT 而不是 VARCHAR 存储数字
-- 使用 VARCHAR(100) 而不是 VARCHAR(1000)

-- 2. 垂直拆分
-- 将大字段拆分到单独的表
CREATE TABLE users (id INT PRIMARY KEY, name VARCHAR(100));
CREATE TABLE users_detail (user_id INT, profile TEXT);

-- 3. 水平拆分
-- 将大表按条件拆分到多个表
CREATE TABLE orders_2024 (LIKE orders);
CREATE TABLE orders_2025 (LIKE orders);
```


## 九、调优案例

### 9.1 案例1：全表扫描优化

```sql
-- 问题查询
EXPLAIN SELECT * FROM users WHERE name LIKE '%张%';
-- type: ALL, rows: 10000

-- 优化方案1：添加索引
CREATE INDEX idx_name ON users(name);
EXPLAIN SELECT * FROM users WHERE name LIKE '%张%';
-- type: index, rows: 10000

-- 优化方案2：使用全文索引
ALTER TABLE users ADD FULLTEXT INDEX ft_name (name);
EXPLAIN SELECT * FROM users WHERE MATCH(name) AGAINST('张');
-- type: fulltext
```

### 9.2 案例2：临时表优化

```sql
-- 问题查询
EXPLAIN SELECT name, COUNT(*) FROM users GROUP BY name;
-- Extra: Using temporary, Using filesort

-- 优化方案：添加索引
CREATE INDEX idx_name ON users(name);
EXPLAIN SELECT name, COUNT(*) FROM users GROUP BY name;
-- Extra: Using index
```

### 9.3 案例3：多表连接优化

```sql
-- 问题查询
EXPLAIN SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
-- orders 表 type: ALL（全表扫描，因为 user_id 没有索引）

-- 优化方案：添加索引
CREATE INDEX idx_user_id ON orders(user_id);
EXPLAIN SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
-- orders 表 type: ref（通过普通索引匹配，可能返回多行）

-- 如果 user_id 是唯一索引，则会显示：
-- orders 表 type: eq_ref（通过唯一索引匹配，每次只返回一行）
```


## 十、监控与告警

### 10.1 慢查询监控

SHOW GLOBAL STATUS LIKE 'Slow_queries';

```

-- 查看索引使用情况
SELECT * FROM sys.schema_index_statistics
ORDER BY rows_selected DESC;
```


## 十一、WITH语句（CTE）优化

### 11.1 WITH语句基础

WITH语句（Common Table Expression，公用表表达式）是MySQL 8.0+支持的特性，用于定义临时结果集。

**基本语法：**
```sql
-- 非递归CTE
WITH cte_name AS (
    SELECT ...
)
SELECT * FROM cte_name;

-- 递归CTE
WITH RECURSIVE cte_name AS (
    -- 锚点成员（初始查询）
    SELECT ...
    UNION ALL
    -- 递归成员
    SELECT ... FROM cte_name WHERE ...
)
SELECT * FROM cte_name;
```

**示例：**
```sql
-- 查找所有部门的员工数量
WITH dept_stats AS (
    SELECT dept_id, COUNT(*) as emp_count
    FROM employees
    GROUP BY dept_id
)
SELECT d.name, ds.emp_count
FROM departments d
JOIN dept_stats ds ON d.id = ds.dept_id;

-- 递归查询：查找组织架构树
WITH RECURSIVE org_tree AS (
    SELECT id, name, manager_id, 1 as level
    FROM employees
    WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, ot.level + 1
    FROM employees e
    JOIN org_tree ot ON e.manager_id = ot.id
)
SELECT * FROM org_tree;
```

### 11.2 WITH语句优化策略

**1. 避免重复计算**

```sql
-- 差：子查询重复执行
SELECT * FROM (
    SELECT dept_id, AVG(salary) as avg_salary
    FROM employees
    GROUP BY dept_id
) t1
JOIN (
    SELECT dept_id, COUNT(*) as emp_count
    FROM employees
    GROUP BY dept_id
) t2 ON t1.dept_id = t2.dept_id;

-- 好：CTE只计算一次
WITH dept_stats AS (
    SELECT dept_id, 
           AVG(salary) as avg_salary,
           COUNT(*) as emp_count
    FROM employees
    GROUP BY dept_id
)
SELECT * FROM dept_stats;
```

**2. 提升可读性**

```sql
-- 差：嵌套子查询难以阅读
SELECT * FROM (
    SELECT * FROM (
        SELECT * FROM employees WHERE status = 'active'
    ) t1 WHERE salary > 5000
) t2 WHERE dept_id = 1;

-- 好：CTE逻辑清晰
WITH active_employees AS (
    SELECT * FROM employees WHERE status = 'active'
),
high_salary AS (
    SELECT * FROM active_employees WHERE salary > 5000
)
SELECT * FROM high_salary WHERE dept_id = 1;
```

**3. 递归CTE优化**

```sql
-- 差：无限递归
WITH RECURSIVE tree AS (
    SELECT id, name, manager_id
    FROM employees
    UNION ALL
    SELECT e.id, e.name, e.manager_id
    FROM employees e
    JOIN tree t ON e.manager_id = t.id
)
SELECT * FROM tree;

-- 好：添加递归深度限制
WITH RECURSIVE tree AS (
    SELECT id, name, manager_id, 1 as depth
    FROM employees
    WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, t.depth + 1
    FROM employees e
    JOIN tree t ON e.manager_id = t.id
    WHERE t.depth < 10  -- 限制递归深度
)
SELECT * FROM tree;
```

### 11.3 WITH语句执行计划

```sql
-- 查看CTE执行计划
EXPLAIN
WITH cte AS (
    SELECT * FROM employees WHERE dept_id = 1
)
SELECT * FROM cte;

-- 查看CTE的额外信息
EXPLAIN ANALYZE
WITH cte AS (
    SELECT * FROM employees WHERE dept_id = 1
)
SELECT * FROM cte;
```

**执行计划分析：**
- CTE可能被优化器合并到主查询中
- 如果CTE被多次引用，可能会被物化（Materialized）
- 递归CTE会执行多次，需要注意性能

### 11.4 WITH语句 vs 子查询 vs 临时表

| 特性 | WITH语句 | 子查询 | 临时表 |
|------|----------|--------|--------|
| 可读性 | 高 | 低 | 中 |
| 性能 | 好 | 一般 | 好 |
| 复用性 | 可复用 | 不可复用 | 可复用 |
| 索引支持 | 有限 | 有限 | 支持 |
| 递归查询 | 支持 | 不支持 | 不支持 |

**选择建议：**
- 简单查询：使用子查询
- 复杂查询：使用WITH语句提高可读性
- 多次复用：使用临时表
- 递归查询：使用WITH RECURSIVE

### 11.5 WITH语句常见优化场景

**1. 分组统计**

```sql
-- 优化前：多次扫描表
SELECT dept_id, COUNT(*), AVG(salary)
FROM employees
GROUP BY dept_id;

-- 优化后：使用CTE
WITH dept_stats AS (
    SELECT dept_id, 
           COUNT(*) as emp_count,
           AVG(salary) as avg_salary
    FROM employees
    GROUP BY dept_id
)
SELECT * FROM dept_stats WHERE emp_count > 10;
```

**2. 多表连接**

```sql
-- 优化前：复杂嵌套
SELECT * FROM (
    SELECT e.*, d.name as dept_name
    FROM employees e
    JOIN departments d ON e.dept_id = d.id
) t1
JOIN (
    SELECT dept_id, AVG(salary) as avg_salary
    FROM employees
    GROUP BY dept_id
) t2 ON t1.dept_id = t2.dept_id;

-- 优化后：使用CTE
WITH emp_dept AS (
    SELECT e.*, d.name as dept_name
    FROM employees e
    JOIN departments d ON e.dept_id = d.id
),
dept_stats AS (
    SELECT dept_id, AVG(salary) as avg_salary
    FROM employees
    GROUP BY dept_id
)
SELECT ed.*, ds.avg_salary
FROM emp_dept ed
JOIN dept_stats ds ON ed.dept_id = ds.dept_id;
```

**3. 递归查询优化**

```sql
-- 查找所有层级的组织架构
WITH RECURSIVE org_tree AS (
    -- 锚点：顶级节点
    SELECT id, name, manager_id, 1 as level, CAST(name AS CHAR(1000)) as path
    FROM employees
    WHERE manager_id IS NULL
    
    UNION ALL
    
    -- 递归：子节点
    SELECT e.id, e.name, e.manager_id, ot.level + 1,
           CONCAT(ot.path, ' -> ', e.name)
    FROM employees e
    JOIN org_tree ot ON e.manager_id = ot.id
    WHERE ot.level < 5  -- 限制深度
)
SELECT * FROM org_tree ORDER BY path;
```

## 十二、LATERAL 派生表

### 12.1 LATERAL 基础

MySQL 8.0.14+ 支持 LATERAL 关键字，允许派生表（子查询）引用 FROM 子句中先前表的列，实现"横向"关联查询。

**基本语法：**
```sql
-- 语法1：逗号 + LATERAL
SELECT ...
FROM t1, LATERAL (SELECT ... FROM t2 WHERE t2.col = t1.col) AS alias
WHERE ...

-- 语法2：JOIN + LATERAL
SELECT ...
FROM t1 JOIN LATERAL (SELECT ... FROM t2 WHERE t2.col = t1.col) AS alias ON ...
WHERE ...
```

**与普通子查询的区别：**
- 普通子查询：独立执行，不能引用外部表的列
- LATERAL 子查询：可以引用 FROM 子句中先前表的列，每行执行一次

### 12.2 LATERAL 示例

**示例1：查询每个用户的最新订单**
```sql
-- 表结构
CREATE TABLE users (id INT PRIMARY KEY, name VARCHAR(100));
CREATE TABLE orders (id INT PRIMARY KEY, user_id INT, amount DECIMAL(10,2), create_time DATETIME);

-- 方式1：普通子查询（无法关联外部表）
SELECT u.name, o.amount, o.create_time
FROM users u, (
    SELECT user_id, amount, create_time
    FROM orders
    WHERE create_time = (SELECT MAX(create_time) FROM orders WHERE user_id = orders.user_id)
) o
WHERE u.id = o.user_id;

-- 方式2：LATERAL 子查询（可以关联外部表）
SELECT u.name, o.amount, o.create_time
FROM users u, LATERAL (
    SELECT amount, create_time
    FROM orders
    WHERE user_id = u.id
    ORDER BY create_time DESC
    LIMIT 1
) o;

-- 方式3：JOIN + LATERAL
SELECT u.name, o.amount, o.create_time
FROM users u
JOIN LATERAL (
    SELECT amount, create_time
    FROM orders
    WHERE user_id = u.id
    ORDER BY create_time DESC
    LIMIT 1
) o ON 1=1;
```

**示例2：查询每个部门薪资最高的员工**
```sql
-- 表结构
CREATE TABLE departments (id INT PRIMARY KEY, name VARCHAR(100));
CREATE TABLE employees (id INT PRIMARY KEY, name VARCHAR(100), dept_id INT, salary DECIMAL(10,2));

-- 使用 LATERAL 查询每个部门薪资最高的员工
SELECT d.name AS dept_name, e.name AS emp_name, e.salary
FROM departments d, LATERAL (
    SELECT name, salary
    FROM employees
    WHERE dept_id = d.id
    ORDER BY salary DESC
    LIMIT 1
) e;

-- 使用 LATERAL + JOIN
SELECT d.name AS dept_name, e.name AS emp_name, e.salary
FROM departments d
JOIN LATERAL (
    SELECT name, salary
    FROM employees
    WHERE dept_id = d.id
    ORDER BY salary DESC
    LIMIT 1
) e ON 1=1;
```

**示例3：LATERAL 与 UNTIL（MySQL 8.0.14+）**
```sql
-- 查询每个用户连续登录的天数
-- 表结构
CREATE TABLE user_logins (id INT PRIMARY KEY, user_id INT, login_date DATE);

-- 使用 LATERAL + 递归CTE 计算连续登录天数
WITH RECURSIVE login_streak AS (
    SELECT user_id, login_date, login_date AS start_date, 1 AS streak
    FROM user_logins
    WHERE login_date = (SELECT MIN(login_date) FROM user_logins WHERE user_id = user_logins.user_id)
    
    UNION ALL
    
    SELECT l.user_id, l.login_date, ls.start_date, ls.streak + 1
    FROM user_logins l
    JOIN login_streak ls ON l.user_id = ls.user_id
    WHERE l.login_date = DATE_ADD(ls.login_date, INTERVAL 1 DAY)
)
SELECT user_id, MAX(streak) AS max_streak
FROM login_streak
GROUP BY user_id;
```

### 12.3 LATERAL 使用场景

| 场景 | 说明 | 示例 |
|------|------|------|
| Top-N 查询 | 每组取前N条 | 每个部门薪资最高的3名员工 |
| 最新记录 | 每组取最新一条 | 每个用户的最新订单 |
| 累计计算 | 每行关联前面的累计结果 | 计算累计销售额 |
| 行转列 | 动态生成列 | 将多行数据转为一行的多列 |

### 12.4 LATERAL vs 子查询 vs JOIN

| 特性 | LATERAL | 普通子查询 | JOIN |
|------|---------|------------|------|
| 引用外部表列 | 支持 | 不支持 | 支持 |
| 执行方式 | 每行执行一次 | 独立执行 | 合并执行 |
| 性能 | 适合小数据量 | 适合大数据量 | 适合大数据量 |
| 限制 | 不能用于INSERT/UPDATE | 无特殊限制 | 无特殊限制 |

**选择建议：**
- 需要引用外部表列时：使用 LATERAL
- 数据量大且无关联：使用普通子查询或 JOIN
- 需要Top-N或最新记录：LATERAL + LIMIT 效率高

### 12.5 LATERAL 性能优化

```sql
-- 1. 确保关联列有索引
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_employees_dept_id ON employees(dept_id);

-- 2. 使用 LIMIT 限制结果集
SELECT u.name, o.amount
FROM users u, LATERAL (
    SELECT amount
    FROM orders
    WHERE user_id = u.id
    ORDER BY create_time DESC
    LIMIT 1
) o;

-- 3. 避免 LATERAL 子查询过于复杂
-- 差：子查询太复杂，多次访问 orders 表
SELECT u.name, o.amount, o.create_time
FROM users u, LATERAL (
    SELECT amount, create_time
    FROM orders o1
    WHERE o1.user_id = u.id
    AND o1.create_time > DATE_SUB(NOW(), INTERVAL 30 DAY)
    AND o1.amount > 100
    ORDER BY o1.create_time DESC
    LIMIT 1
) o;

-- 好：先筛选再关联，减少 LATERAL 子查询的扫描量
WITH recent_orders AS (
    SELECT user_id, amount, create_time
    FROM orders
    WHERE create_time > DATE_SUB(NOW(), INTERVAL 30 DAY)
    AND amount > 100
)
SELECT u.name, ro.amount, ro.create_time
FROM users u, LATERAL (
    SELECT amount, create_time
    FROM recent_orders
    WHERE user_id = u.id
    ORDER BY create_time DESC
    LIMIT 1
) ro;
```


## 十三、总结

### 13.1 调优流程

1. **慢查询日志**：定位执行时间长的 SQL
2. **EXPLAIN 分析**：查看执行计划
3. **检查 type**：确保达到 range 级别，最好达到 ref
4. **检查 key**：确保使用了合适的索引
5. **检查 Extra**：避免 Using temporary 和 Using filesort
6. **检查 Rows**：确保扫描行数合理
7. **优化 SQL**：添加索引、改写查询
8. **验证效果**：再次 EXPLAIN 确认优化效果

### 13.2 优化原则

- 避免全表扫描（ALL）
- 确保使用索引（key 不为 NULL）
- 减少扫描行数（rows 越小越好）
- 使用覆盖索引（Using index）
- 避免临时表和文件排序
- 选择合适的索引类型

### 13.3 常见优化场景

| 场景           | 问题     | 优化方案               |
|----------------|----------|------------------------|
| LIKE '%xxx%'   | 索引失效 | 使用全文索引或搜索引擎 |
| 函数操作索引列 | 索引失效 | 避免函数操作           |
| OR 查询        | 索引失效 | 改用 UNION             |
| 不等于查询     | 索引失效 | 改用 IN 或 > <         |
| 类型转换       | 索引失效 | 避免隐式类型转换       |
